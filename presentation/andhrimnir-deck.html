AI incident intelligence for restaurants

Operational writes raise incidents, the platform explains them with bounded evidence, and an advisory layer recommends next actions. Nothing is mutated by model output.

Repository

DineSmart — Next.js frontend, Express 5 + TypeScript API, MongoDB.

Format

10-minute talk, 5-minute live demo, one presenter.

Team

Frontend, backend, AI integration, and documentation/QA owners.

Honest baseline

Locally verified on Node 24.21.0; deployment is deferred, not claimed.

Presenter: lead with a single detected incident. The deck is a preparation artifact — the demo has not been rehearsed against live services.

Slide 2 · 0:45–1:45

Incidents are discovered by customers, not systems

  • Service delays surface as complaints long after the kitchen fell behind.
  • Stock-outs are noticed when a dish cannot be served, not when a threshold is crossed.
  • Reservation conflicts and blocked tables appear at the door.
  • Existing dashboards show state — tables, orders, counts — but not the cause or the next action.

Presenter: quantify with one local example (a 25-minute-old preparation item) rather than industry statistics.

Slide 3 · 1:45–2:30

Detect → contextualize → recommend → observe

  • Detect: operational writes and scheduled sweeps evaluate rule-managed conditions with configurable thresholds.
  • Contextualize: each incident stores a bounded, tenant-scoped trigger snapshot — never free-text customer data.
  • Recommend: Gemini generates advisory actions; a deterministic fallback keeps the flow usable when the provider is unavailable.
  • Observe: incidents resolve automatically when the trigger clears, and a recurrence opens a fresh record.

Presenter: always say “advisory”. Model output never mutates operational records.

Slide 4 · 2:30–3:15

Architecture

Frontend

Next.js 16 App Router, React 19, role-aware workspace with explicit states.

API

Express 5 + TypeScript under /api/v1, stateless and tenant-scoped.

Data

Official MongoDB Node driver, projected bounded reads, documented indexes.

Realtime

WebSocket transport with ticketed auth and ACK-based delivery persistence.

Advisory layer

Isolated provider module with strict output validation and fallback rules.

Scheduling

Event hooks plus hourly sweeps for incidents and the health score.

Presenter: point at the SDD diagram if the projector allows; otherwise describe the request path in one sentence.

Slide 6 · 4:15–5:15

Incident intelligence

kitchen_delay order_delay kitchen_congestion inventory_shortage reservation_conflict queue_congestion table_congestion
  • Bounded detection: 2,000-record source scans, 200-record API responses, explicit truncation flags.
  • One active record per restaurant, type, and affected entity; severity and evidence update in place.
  • Automatic resolution when the condition clears; a recurrence opens a fresh identifier.
  • Queue and table congestion use the waitlist: party count, longest wait, and whether any free table can seat the largest waiting party.

Presenter: staff-shortage detection is deliberately absent — it has no input in the current data model.

Slide 8 · 6:00–6:45

Operational analytics

  • 7d and 30d windows with restaurant-local time buckets.
  • Order, reservation, and preparation counts — operational volume, not revenue.
  • Truncation is explicit: capped series are labelled rather than silently complete.

Presenter: never call pre-bill subtotals revenue. Payment capture is out of scope by design.

Slide 9 · 6:45–7:30

Engineering quality

Static checks

Biome lint/format and tsc --noEmit across both packages.

Tests

300 backend and 38 frontend tests on the Node test runner, co-located with modules.

CI

Frontend, backend, and preflight jobs on Node 24.21.0 with lockfile installs and audits.

Secrets

Placeholder-only .env.example files; no credentials committed.

Browser pass

7 routes × 3 viewports: zero page errors, no horizontal overflow, 24 px minimum hit areas.

Resilience

Presenter: these are local CI-equivalent checks — no GitHub Actions run has been observed because no remote is configured.

Slide 10 · 7:30–10:00

Live demo

  1. Customer browses the menu and places an order.
  2. Kitchen advances preparation; the order status is visible to the guest.
  3. A threshold is crossed and an incident opens with its trigger snapshot.
  4. Manager opens the incident and requests advisory recommendations.
  5. Reservation and waitlist flows seat a party and free a table.

Presenter: follow the runbook. If a service is unavailable, narrate the fallback — sample content stays visibly labelled as preview.

Slide 11 · 10:00–11:00

Roadmap and stated limits

  • Not built: payments or payment capture; pre-bill subtotals are not revenue.
  • Not verified: live MongoDB/Atlas, indexes under real data, Gemini with a live key.
  • Deferred: deployment (S3-08/S3-09) until the remaining non-deployment work is finished.
  • Open: notification recipient policy, retention, wait-estimate formula, staff-shortage detection.
  • Next: seeded database rehearsal, recorded backup demo, then deployment.

Presenter: close on boundaries. Judges respond better to stated limits than to overclaiming.
